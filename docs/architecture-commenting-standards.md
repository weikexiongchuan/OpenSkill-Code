# 设计意图入码规范

适用于所有语言、所有实现角色。目标是让人和 AI 在读取代码时，能直接看到复杂实现的原因、边界、扩展点和早期预留接口，而不是只看到“现在怎么跑”。

## 何时必须写注释

以下情况不能只写代码，必须补充临近注释：

1. 方法内部存在非直觉流程、分阶段处理、补偿逻辑、降级逻辑
2. 代码实现背后有明确设计权衡，且从命名上看不出来
3. 当前实现为了后续扩展预留了接口、抽象层、插槽、策略位
4. 某段结构受上游协议、兼容性、性能、幂等性、时序约束影响
5. 暂时保留的折中方案，未来有明确替换方向

## 注释要写什么

优先写“为什么”和“以后怎么扩”，少写“这行代码做了什么”。

- **设计意图**：这一段是为了解决什么问题
- **约束条件**：不能轻易改动的原因是什么
- **扩展方向**：未来新增能力时，应该从哪里接入
- **接口边界**：哪些参数、返回值、抽象层是故意保留的
- **替换条件**：什么情况下可以重构或替换当前实现

## 推荐写法

### 1. 方法内部复杂逻辑前写块注释

适用于多阶段流程、容错逻辑、状态机、异步拼接等复杂实现。

```java
// Design note:
// 这里先做本地去重，再做远端校验，是为了降低热点请求下的外部依赖压力。
// 当前保留 verifyRemotely(...) 这一层，而不是直接内联 HTTP 调用，
// 是为了后续接入批量校验、缓存旁路和多供应商策略。
```

### 2. 预留接口或抽象时写清扩展入口

适用于策略模式、适配器、SPI、插件点、provider registry。

```python
# Extension point:
# 当前只注册 DefaultScorePolicy，但注册表接口保持不变。
# 后续如果引入链级别差异策略，优先扩展 policy_registry，
# 不要把条件分支继续堆回调用方。
```

### 3. 结构性约束放在类型/模块入口

适用于核心聚合根、服务编排器、网关、公共 DTO、数据库模型。

```ts
/**
 * Architecture note:
 * SignalAssembler 负责拼装只读视图，不承担持久化和规则判定。
 * 后续增加更多 signal enrichment 时，继续通过 enrichers 注入，
 * 不要在 assembler 内直接耦合新的数据源客户端。
 */
```

## 架构设计师职责

在设计阶段必须显式产出以下内容，并要求开发实现时落到代码中：

1. **扩展点清单**：哪些位置预计会增长能力，为什么
2. **接口预留策略**：当前先保留哪一层抽象，不提前过度泛化，但要给未来接入留口
3. **不可破坏约束**：哪些结构不能被后续开发随意绕过
4. **注释落点**：哪些类、方法、流程段必须把设计意图写进代码

## 长任务错误覆盖规范

涉及多阶段、异步、跨服务或可恢复状态的长任务，设计完成前必须先画出完整业务链路，并逐阶段建立失败矩阵；不得只设计成功路径，也不得等线上出现异常后再补分支。

失败矩阵必须覆盖每个可观察、可控制的操作，以及无法预先分类的未知异常：

- **失败来源**：输入与前置条件、业务数据状态、外部请求与协议、认证与限流、超时与断连、资源与容量、数据库事务与并发、消息重复与乱序、租约过期、进程退出与重启、结果成功但响应丢失、补偿或恢复失败。
- **异常定义**：实际可能抛出的异常、错误码、HTTP 状态、关闭事件或校验结果；不得用一个笼统异常吞掉不同业务语义。
- **状态迁移**：每类错误发生前后的任务状态、子任务状态和持久化事实，包含重复执行和旧事件到达时的处理。
- **处置规则**：明确哪些重试、最多几次、何时终止、何时需要补偿、如何恢复；存在多种合理业务语义时必须先让用户确认。
- **可观测证据**：日志、指标、任务字段和告警必须能定位到失败阶段、对象、次数和最终结果，且不得泄露敏感信息。
- **测试映射**：按 [最小验证原则](testing-scope.md) 覆盖本次实际改变的关键失败路径，相关未变路径复用已有证据；不为局部修复重验完整矩阵，关键风险缺证据时只阻断受影响部分。

设计必须保留未知异常的显式失败路径：记录完整内部上下文并对外返回安全错误，使任务进入可诊断状态；禁止静默跳过、伪装成功或无限重试。

## 开发实现职责

开发用 AI 或人工实现时，除了完成功能，还要同步写入以下信息：

- 在复杂方法内部补 `Design note` / `Architecture note` / `Extension point`
- 在预留接口附近说明“现在只实现了什么，未来从哪里扩”
- 在临时折中方案旁说明触发重构的条件
- 在模块入口说明职责边界，避免后续逻辑倒灌

## 读取代码做后续设计时的原则

后续做架构设计、重构或功能扩展时，先读代码中的这些注释，再读外部设计文档：

1. 先找 `Design note`
2. 再找 `Architecture note`
3. 再找 `Extension point`
4. 最后再决定是否重做抽象

如果代码与外部文档冲突，以“最新代码 + 临近注释”作为一线事实，再回写 workspace/设计文档。

## 禁止事项

- 禁止把关键设计意图只留在聊天记录，不进代码
- 禁止写大段空话注释，必须指向真实约束或扩展方案
- 禁止为了“预留”制造无业务价值的过度抽象
- 禁止注释和实现长期背离；代码变更时同步改注释
