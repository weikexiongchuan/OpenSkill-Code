# 日志规范与检索约定

适用于每个新增或改动的业务处理模块。优先复用项目现有日志框架和采集系统；标签与上下文字段应能让人和 AI 用同一套稳定查询定位问题。纯静态展示或不产生持久化日志的代码库无独立轮转对象，应注明“不适用”；有业务处理的浏览器功能应使用项目现有可持久化的前端日志/错误上报链路，不能把临时 `console` 输出当成可复盘日志。

## 设计与输出

1. 每个**产生持久化日志的模块**都要有已验证的日志回收机制：本地文件配置按大小/日期轮转、保留期和容量上限；标准输出由容器/systemd/集中采集系统托管时，确认对应轮转、保留和容量策略。共享机制可以覆盖多个模块，不必重复建日志文件，但不能只有写入没有回收。
2. 新功能在关键节点记录开始/接收、关键决策、外部调用结果、完成或失败；异步流程记录入队、消费、重试、终态。按业务吞吐选择单对象、批次或汇总粒度：高频成功路径不得对每条事件的每个阶段都打 `INFO`，可用已有的采样、汇总或低级别诊断策略；失败逐条保留可关联证据。设计时估算峰值日志量、写入负载与回收容量，不逐条打印高频内部循环或完整大对象。
3. 日志消息前缀使用稳定的方括号标签：`[业务][子流程][阶段]`；例如 `[signal][quote][match]`。标签使用固定小写词，不在标签中塞 ID、时间戳、用户输入或高基数字段。每个业务维护少量稳定标签，同类事件沿用同一组标签。
4. **所有错误日志统一带 `[error]`**，并保留业务/阶段标签，例如 `[error][signal][quote][match]`；使用 `error` 级别，记录异常类型、完整堆栈、失败阶段、可安全记录的对象 ID、请求/任务关联 ID 和结果。已在边界记录的同一异常避免层层重复打印。
5. 时间戳（含时区）、级别、模块/服务名由日志框架统一输出；业务 ID、链、CA、消息 ID、事务 ID 等作为结构化字段或稳定的 `key=value` 上下文，而不是动态标签。禁止记录密钥、令牌、Cookie、个人敏感信息或未经脱敏的请求体。
6. 在项目 `workspace/{project}/common/` 维护日志标签索引：每个业务记录固定标签、各标签代表的阶段、关联字段和对应代码位置；新增或改名时同步更新，避免 AI 查询时猜测同义词。已存在可靠索引时引用原位置，不重复建表。

## 为 AI 查询日志设计的路径

1. 先用 `[error]` + 时间窗口做每日巡检，按模块标签、错误类型和关联 ID 聚合；标签按**字面量**匹配（例如 `rg -F '[error]'`，日志平台使用等价精确查询），避免正则把方括号当字符类。`[error]` 不得用于普通告警或预期分支。
2. 定位具体故障时依次缩小：`[业务]` → `[子流程]` → `[阶段]` → 关联 ID；用同一关联 ID 回看接收、决策、下游响应和最终状态。
3. 一次链路应能从日志区分“未收到”“已收到但未处理”“处理失败”“已完成”；如果仅凭日志无法区分，在关键节点补证据字段或日志，而不是扩大日志量。
4. 验收时用真实日志或测试环境样本跑一遍上述查询；核对标签稳定性、错误日志统一命中、关联链路可追溯，以及适用模块的轮转/保留配置实际生效。适用模块未接入回收或查不到关键阶段，视为未完成。
