# 项目约束的识别与维护

OpenSkill 提供理解项目、识别证据、归档和维护约束的方法。具体约束由项目现有规则、用户明确要求和已确认的设计决定；不预设所有项目使用同一监控平台、发布流程或业务机制。

## 何时使用

- 首次理解项目、进入不熟悉的模块，或当前任务依赖尚未核实的项目规则时，读取相关规则和实现证据。
- 用户明确长期约定、纠正可重复出现的偏差，或实际工作产生有复用价值的稳定结论时，按下述分类选择是否归档。
- 已知项目的小修改只核对命中的规则和证据，不重新扫描全仓；纯提问、一次性操作、临时讨论不自动生成 AGENTS 或笔记。

## 先读项目，再判断信息性质

先确认目标项目根目录和涉及模块，读取适用的 AGENTS.md、CLAUDE.md、已有规范索引及命中主题。只按需核对相关代码、配置、测试、构建文件或操作脚本，不执行部署、外部写入或生产操作来收集规则。

| 信息性质 | 证据 | 处理方式 |
|---|---|---|
| 已有明确约束 | 适用项目规则、用户明确要求、已确认且适用的设计约束 | 直接遵循；需要整理时沿用来源和范围，不重复确认 |
| 当前事实 | 代码、配置、测试或脚本证明当前如何工作 | 需要复用时记录为事实，附证据；不能自动写成“必须/禁止” |
| 候选约束 | 从重复模式、实现结构或问题中推断值得长期保留的规则 | 标为候选，说明依据和影响；没有明确依据前不作为执行门禁 |
| 单次决定或临时信息 | 仅适用于本次操作的参数、试验、排障步骤 | 留在本次任务记录，不转成长期约束 |

代码中三处采用同一种做法，仍只证明存在重复模式。已有实现缺陷、测试缺口、过时注释或未完成方案不构成应沿用的规范。

例如：“当前使用 Grafana”是项目事实；用户明确要求“新增调用复用项目现有监控服务”才是项目约束。当前发布脚本的行为也不能自动成为其他项目的发布要求。

## 逐步沉淀到项目已有位置

使用 `standards-organizer` 归档，使用 `project-state-record-update` 维护相关事实与索引。两者遵循同一套分类，不另建一套固定目录或规范体系。

- 优先更新项目已有的规则文档和索引；如果仓库已维护 AGENTS、CLAUDE、docs 或 notes，沿用其分工，不再在 OpenSkill workspace 复制同一条规则。
- AGENTS / CLAUDE 保留适用范围、关键约束和按任务读取的入口；较长的协议、流程和说明放已有主题文档，通过链接引用。没有入口文件时，仅在当前任务确需建立入口时创建。
- 项目事实、可复用能力及待核实事项放已有项目记录；没有既定记录位置且本次确需持久化时，再按 workspace protocol 选择位置。
- 每条正式约束保留简短的适用范围和来源。事实附代码/配置/测试等证据位置；候选条目明确“待确认”及影响，不混入正式规则。
- 用户已明确的长期约定和稳定纠偏可直接归档；范围不明或会新增职责、功能、验证门禁、运行依赖时，仅询问受影响的具体决定。其余已授权工作继续，候选未回复不视为同意或拒绝。
- 不要求每次工作都新增规则。已有规则一致时复用；同一信息只保留一处，其余位置写引用。

条目可按现有格式简写为：`规则或事实；适用范围；来源/证据；状态（候选时注明）`，无需为归档新增机器 schema 或检查程序。

## 后续使用与更新

1. 后续任务先读适用入口，再读命中主题；实现或配置事实需要时用当前文件核实，笔记不能替代实际证据。
2. 用户明确修订原规则时更新原条目，保留必要来源，不再询问同一选择。只修订本次明确覆盖的范围。
3. 文档与实现不一致时，分别说明规定和实际行为。不能只因代码变化就撤销规则，也不能仅凭旧文档声称当前实现已符合。
4. 来源不足的冲突或疑似过时条目标为待核实；影响本次目标时说明具体差异并澄清，只暂停依赖该决定的部分。
5. 已有明确替代依据时修订失效条目，并同步索引和引用。修正规则文档不授权业务改造、历史迁移、部署或生产写入。

## 项目规则与通用层的边界

沉淀项目规则不触发向 OpenSkill 通用技能迁移。仅在实际多项目复用有依据、且用户要求整理通用能力时，评估是否抽取；已有通用规范直接引用。项目采用的 Grafana、JAR 发布方式、服务器、数据库、信号推送和账号导入流程都不能因一次沉淀而成为跨项目要求。

完成整理时说明：实际更新位置、依据和适用范围、候选与未核实项；仅补文档不声称已完成业务实现或运行验证。
