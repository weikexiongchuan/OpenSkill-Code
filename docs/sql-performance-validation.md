# SQL 设计与性能验收

适用于新增或修改的原生 SQL、ORM/查询构造器生成的 SQL、批处理和迁移脚本；先取得最终 SQL 和真实参数类型，再评估，不能只审查方法名。

## 设计时

1. 列出每条 SQL 的表、过滤条件、关联、排序、分页、调用频率、单次/长期数据量和事务边界；核对现有索引定义，优先复用索引。
2. 让高频查询的过滤、关联、排序尽量命中合适索引。联合索引按实际条件和排序设计，不能只因为字段上“有索引”就判定可用；同时评估新增索引的写入、空间和维护成本。
3. 对分页、批量更新/删除和后台长任务明确单批上限、游标/分片、锁范围与事务提交点，避免全量扫描、长事务和锁等待累积。
4. 若业务确需全表扫描或无法建有效索引，记录数据规模、调用频率、实测成本和原因；不得把未验证的例外当成正常通过。

## 开发完成后的必验步骤

1. 建立本次 SQL 清单，包含 ORM 实际生成语句、参数类型、对应代码位置及目标索引；没有 SQL 改动则记为“不适用”。
2. 先用表结构/索引定义确认索引存在；对数据库支持执行计划的查询/DML，用代表性参数和接近真实的数据量执行 `EXPLAIN`，记录索引、访问类型、估计扫描行数和排序/临时表。安全的只读查询可在合适环境补 `EXPLAIN ANALYZE`，记录实际扫描行数与耗时；它会真实执行语句，带副作用的语句只允许在隔离测试库分析。DDL 不适用执行计划，改为在隔离库验证迁移耗时、元数据锁和回滚/恢复路径。`key` 为空或 `type=ALL` 的目标库查询不能直接执行，先优化或明确暂停并报告；不能靠添加 `LIMIT` 掩盖扫描。
3. **实际预执行**每条 SQL，验证语法、绑定参数、返回/影响行数和耗时。只读 SQL 在获准且符合索引约束的目标环境执行；写入、DDL、会触发副作用的查询只在隔离测试库验证。生产 DDL/DML 必须另行列明目标库表、完整操作及影响范围，并取得该次明确同意；测试库成功不等于生产执行授权。
4. 对长期运行路径用预期数据规模、调用频率与批次数估算总时长，检查事务跨度、锁等待、连接占用、超时、回滚代价和并发下的写入放大。必要时在隔离环境做多批/并发实测，不以单次快速执行代替长期风险评估。
5. 在实现/验收记录里给出每条 SQL 的执行环境、参数口径、实测耗时和长事务风险；适用语句记录执行计划、扫描行数和索引结论，DDL 记录执行计划不适用及隔离库迁移/锁/恢复结果。未能预执行或性能不达标则标记未通过，不得写成“已验证”。
