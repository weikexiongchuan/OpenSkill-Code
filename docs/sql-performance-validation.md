# SQL 设计与性能验收

适用于新增或修改的原生 SQL、ORM/查询构造器生成的 SQL、批处理和迁移脚本；先取得最终 SQL 和真实参数类型，再评估，不能只审查方法名。

## 设计时

1. 列出每条 SQL 的表、过滤条件、关联、排序、分页、调用频率、单次/长期数据量和事务边界；核对现有索引定义，优先复用索引。
2. 让高频查询的过滤、关联、排序尽量命中合适索引。联合索引按实际条件和排序设计，不能只因为字段上“有索引”就判定可用；同时评估新增索引的写入、空间和维护成本。
3. 对分页、批量更新/删除和后台长任务明确单批上限、游标/分片、锁范围与事务提交点，避免全量扫描、长事务和锁等待累积。
4. 若业务确需全表扫描或无法建有效索引，记录数据规模、调用频率、实测成本和原因；不得把未验证的例外当成正常通过。

## 每条最终 SQL 必须做精简与效率复检

来源：2026-10-10 用户纠偏，要求每次写 SQL 后确认是否还有更简单、更高效的等价方式。适用于手写、ORM 生成及工具实际执行的 SQL；参数、查询形状或执行方式变化后重新复检。

1. **先还原目的**：列清真正要读写的数据、业务时间、结果是否需要有序及单次处理边界；不能把工具默认分页或现有写法当作需求。
2. **逐项审必要性**：检查每个过滤条件、JOIN、子查询、排序、分页、候选查询和投影字段；删掉不影响业务正确性、处理边界及数据保护的步骤。保留项说明具体作用，不以“更安全”代替理由。
3. **比较最小等价路径**：先比较直接索引范围处理与“查候选再按 ID 处理”，再考虑复杂分页或新增索引。冻结旧表、唯一自增主键且复制不要求结果有序时，优先评估固定主键区间直接 `INSERT ... SELECT ... WHERE id >= :lo AND id < :hi`；有时间保留条件仍须保留，不能假设 ID 大小等于事件时间。
4. **证明批量有界**：去掉 LIMIT 必须有其他可靠上限。唯一整数主键的半开区间宽度可限制最大行数；只有 `id > :cursor` 没有上界会成为无界读取。非唯一索引的数值区间不能直接当作行数上限，主键空洞也不能当作任务结束。
5. **核对真实访问路径**：读取完整索引定义及有效前缀，EXPLAIN 最终 SQL；不能因为时间字段出现在联合索引里就认定仅时间条件可高效定位。ORDER BY 不必然产生额外排序，须核查 filesort、扫描与回表成本；LIMIT 也不必然低效，不能一律删除。
6. **核对整个批次**：包括边界查询、候选读取、写入和 COMMIT，不只计时主要 DML。可直接有界处理时，避免为了分页重复找边界或搬运大字段到客户端。使用迁移工具也须检查实际生成 SQL，不能只看命令参数。
7. **控制在途数量**：后台批处理先采用串行；上一批数据库执行及事务结束、间隔等待完成后才发下一批。确需并发时写明固定上限、同一工作流共享的限制及负载暂停条件；超时但服务端是否结束未知时不得立即补发或重试，不能把本任务上限说成全库活跃查询保证。
8. **慢了先改路径**：出现慢批、排队或中止，先复检扫描范围、排序、回表、重复查询与并发，再决定调整。不得仅靠加等待、放宽超时或负载阈值反复重跑；已命中索引、小表成功和平均耗时低都不能替代大表高负载适用性判断。

每条 SQL 在现有实现或审核记录中简写复检结论：用途、最简替代及取舍、索引/扫描范围、排序与批量上限、整批实测和在途上限。未完成复检不能标记 SQL 验收通过；不为此另建报告系统或生产探针。同一已审核 SQL 形状内，游标/有界批次正常推进只校验既定参数边界，不重复未变化的全套验收；访问路径可能改变时才补对应执行计划与实测。

## 开发完成后的必验步骤

1. 建立本次 SQL 清单，包含 ORM/工具实际生成语句、参数类型、对应代码位置及目标索引，并逐条完成上述精简与效率复检；没有 SQL 改动则记为“不适用”。
2. 先用表结构/索引定义确认索引存在；对数据库支持执行计划的查询/DML，用代表性参数和接近真实的数据量执行 `EXPLAIN`，记录索引、访问类型、估计扫描行数和排序/临时表。安全的只读查询可在合适环境补 `EXPLAIN ANALYZE`，记录实际扫描行数与耗时；它会真实执行语句，带副作用的语句只允许在隔离测试库分析。DDL 不适用执行计划，改为在隔离库验证迁移耗时、元数据锁和回滚/恢复路径。`key` 为空或 `type=ALL` 的目标库查询不能直接执行，先优化或明确暂停并报告；不能靠添加 `LIMIT` 掩盖扫描。
3. **实际预执行**每条 SQL，验证语法、绑定参数、返回/影响行数和耗时。只读 SQL 在获准且符合索引约束的目标环境执行；写入、DDL、会触发副作用的查询只在隔离测试库验证。生产 DDL/DML 必须另行列明目标库表、完整操作及影响范围，并取得该次明确同意；测试库成功不等于生产执行授权。
4. 对长期运行路径用预期数据规模、调用频率与批次数估算总时长，检查事务跨度、锁等待、连接占用、超时、回滚代价和并发下的写入放大。必要时在隔离环境做多批/并发实测，不以单次快速执行代替长期风险评估。
5. 在实现/验收记录里给出每条 SQL 的执行环境、参数口径、实测耗时和长事务风险；适用语句记录执行计划、扫描行数和索引结论，DDL 记录执行计划不适用及隔离库迁移/锁/恢复结果。未能预执行或性能不达标则标记未通过，不得写成“已验证”。
