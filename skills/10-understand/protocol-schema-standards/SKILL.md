# Protocol Schema Standards

## 核心原则

- **同一业务语义，同一字段名**
- **同一业务语义，同一层级**
- **优先消费者零分支，不优先发布方顺手**
- **模块内部结构差异，不能外溢成协议差异**

## 适用范围

- HTTP / RPC API 出入参
- Redis / MQ / PubSub 事件
- signal / webhook / callback payload
- 跨模块 DTO / VO / response
- 策略配置、规则配置、外部可编辑配置
- 数据库输出给外部系统的只读视图

## 设计步骤

### 1. 先找现有语义

新增字段前先回答：

1. 这次表达的业务语义是什么
2. 系统里是否已有同语义字段
3. 现有字段名、层级、类型是什么

如果已有同语义表达，默认直接复用；不要因为当前模块结构不同就重命名。

### 2. 站在接入方看复杂度

判断标准不是“当前模块怎么实现最顺”，而是：

- 接入方能否按统一字段读取
- 是否会因为事件类型不同而写 if/else
- 是否需要额外映射表做同义归一
- 是否会出现“同义不同名”或“同义不同层级”

如果答案是“会”，优先回到协议侧统一，而不是把转换成本推给接入方。

### 3. 再决定是否允许例外

只有这几类情况才允许例外：

- 已上线协议，改名会破坏兼容
- 第三方协议强约束，无法改
- 同名但语义其实不同，不能硬并

出现例外时，必须明确写出：

- 为什么不能统一
- 影响哪些消费者
- 消费者需要承担什么额外处理

## 强制检查项

### 命名检查

- 同义字段禁止出现两个名字，不要为同一业务语义并存两个字段名
- 禁止把内部存储字段名直接泄漏成对外协议，除非它本来就是公共协议
- 缩写只在全局已有先例时复用，否则优先全称

### 层级检查

- 同义字段禁止一处在顶层、一处在 `snapshot`、另一处在 `data` 里
- 不要因为某个 payload 当前少一层对象，就临时换字段位置
- 如果已有公共 envelope，新增事件优先对齐 envelope，而不是自创结构

### 类型检查

- 同义字段类型必须统一：`string / number / boolean / object / array`
- 数字精度、时间单位、枚举值大小写必须统一
- 同义字段不要一处可空、一处必填，除非语义明确不同

## 常见反模式

| 反模式 | 问题 |
|------|------|
| “这个事件没有 snapshot，所以改叫另一个名字” | 用局部结构差异破坏全局语义一致性 |
| “producer 这边这样组装更方便” | 把复杂度转嫁给 consumer |
| “先发两个名字兼容一下” | 让接入方长期背双字段分支 |
| “当前模块沿用 Redis/DB 字段名” | 内部模型泄漏到外部协议 |

## 输出模板

涉及对外协议变更时，设计或实现说明里至少补一张表：

| 业务语义 | 现有字段 | 候选方案 | 最终采用 | 不采用原因 | 接入影响 |
|------|------|------|------|------|------|

## 自查

1. 这次新增的是不是旧语义换了个新名字
2. 接入方是否能不写分支直接消费
3. 有没有把模块内部结构差异暴露成外部协议差异
4. 字段名、层级、类型、单位是否与既有协议一致
5. 例外情况是否写明兼容原因和接入影响
