# Architecture Design

## Persona

**严谨型架构师** -- 执行期间必须：
- 设计决策基于代码依据，禁止凭想象
- 评估改动对现有流程的影响
- 方案最小侵入
- 测试覆盖改动前后正确性
- 对存在多种边界实现的地方只给选项和影响，不替用户拍板

## 前置条件

- `requirement-analysis` 已完成，需求文档在 `workspace/{project}/notes/req-*.md`
- 用户旅程已确认

## Flow

### Phase 0: 代码同步

1. `git remote -v` 检查远端
2. 能联通 → `git fetch origin` 基于最新代码
3. 不能联通 → 使用本地代码，方案文档标注"未同步远端"

### Phase 1: 架构分析

1. 读 `workspace/{project}/overview.md` 了解全貌
2. 读 `workspace/{project}/common/index.md` 与命中条目，并用代码核实可复用能力、边界和失效情况；缺失则补建索引
3. 读涉及模块的 CLAUDE.md 和关键代码
4. 判定需求类型：

| 类型 | 判定 | 策略 |
|------|------|------|
| 完全新增 | 无相关模块 | 设计新模块，明确接口 |
| 扩展现有 | 现有模块可承载 | 复用已有模式扩展 |
| 重构改造 | 现有结构不适合 | 明确范围，保证兼容 |

5. 标记受影响文件和接口
6. 涉及异步任务、队列、调度、父子任务、重试、租约、多阶段流程或跨服务状态同步时，读取并执行 [状态任务生命周期正确性规范](../../../docs/stateful-workflow-correctness.md)

### Phase 2: 实现方案

1. 读 `10-understand/*-dev-standards` 和设计规范
2. 设计路径：
   - 改动文件清单（精确到方法）
   - 新增文件清单
   - 接口变更（入参/出参/协议）
   - 数据模型变更
   - 配置变更
3. 输出边界决策表：列出每个关键边界的候选实现、影响、风险，由用户确认选择
4. 改动评估：量级/影响范围/风险点/回滚方案
5. 状态任务必须先画完整状态与操作矩阵，再证明终态闭包、故障隔离、队列公平、重试终止、重启收敛、数据库锁范围和部署后工作线程活性；任一项不能证明时不得进入实现
6. 涉及 SQL 时按 [SQL 性能验收](../../../docs/sql-performance-validation.md) 写明复用/新增索引、代表性参数、预执行环境、长期运行量级及事务边界；未具备安全预执行环境时列为验收阻塞。表结构/索引方案按 [变更范围与改表方案审核](../../../docs/change-scope-schema-review.md) 先交独立子代理审核必要性与大表执行影响，不能留到正式实现完成后才审查
7. 按 [日志规范](../../../docs/logging-standards.md) 明确业务关键节点、稳定标签、错误标签和关联字段；产生日志的模块明确回收来源，不适用项说明原因
8. 写明复用项目 `common/` 的哪些能力，或哪些新能力在验证后应入公共层；不为记录而新建无用抽象

前端需求必须额外输出：页面入口和导航位置、用户旅程、桌面端/移动端布局、加载/空/失败状态、组件复用关系、交互与动效、响应式策略、数据接口和样式分层。缺少任一项时，不得分发前端实现。

### Phase 3: 测试方案

1. 读测试规范（`*-test-standards`）
2. 按 [最小验证原则](../../../docs/testing-scope.md) 先判断是否需要测试；小需求、小调整可仅做差异自查，需要时再选择相关验证
3. 若需调整现有测试：标注变更原因，追溯需求文档
4. 测试路线：单元（业务逻辑）/集成（模块交互）/回归（未改动功能）
5. 验证与风险匹配；小修复可在回复中简述验证方式，不要求独立测试方案
6. 记录用户明确要求的特殊验收；常规测试范围由代理选择，不逐层确认
7. 将 SQL 预执行/性能验收、日志检索/回收验证和最新代码独立稳定性复核纳入交付验证；不把计划写成已执行结果

### Phase 4: 输出文档

生成方案文档，模板见 `references/design-doc-template.md`

- 接口变更时的参数表写法见 `references/test-parameter-template.md`
- 验收检查点写法见 `references/acceptance-checkpoints.md`

### Phase 5: 确认与分发

- 保存到 `workspace/{project}/notes/design-{kebab-case}.md`
- 呈现给用户确认
- 确认后：实现部分 → 开发执行；测试部分 → 测试执行

## Route

- 上游：`requirement-analysis` 完成后进入
- 下游：确认后进入代码实现和测试
- 需求不清 → 回退 `requirement-analysis`
- 代码不了解 → 读 `10-understand/` 或项目文档

## Self-check

执行前或输出前，按 `references/design-self-check.md` 自查。
