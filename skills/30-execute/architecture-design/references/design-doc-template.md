# 架构设计文档规范与模板

## 文档结构

- 方案文档只保留“目标”和“方案”两个一级内容章节。
- 目标说明要解决什么问题、达到什么业务结果；方案说明具体怎么做。
- 表字段、接口、流程、代码改动等必要细节放在“方案”内，按实际需要分小节，不为凑模板增加章节。
- 只写当前确定采用的方案，不保留讨论过程、被否决方案、重复背景、代码基线、评估报告、验收清单或待确认事项等附加章节。
- 调研、自查、测试和验证按工作流程实际执行；执行记录不堆入方案文档。
- 目标或方案尚不明确时先沟通，确认后再整理成明确表述。

## 方案设计原则：复用优先、最小必要改动

- 先核对已有表、字段、接口、任务和调度是否能承载需求，再考虑新增结构。
- 在满足正确性和明确业务要求的前提下，优先选择改动范围最小的方案，减少迁移、状态同步和上线风险；不能只按代码行数判断安全性。
- 新增表、聚合任务或独立状态机前，必须用当前代码说明现有结构具体无法满足什么要求；仅为模型完整、范式化或未来扩展不足以成为理由。
- 可通过现有表加字段表达的有限状态，优先就地扩展；不要默认拆成关系表、父任务表和刷数任务表。
- 当业务允许各项独立完成、定期检查维护时，按独立粒度保存结果、暴露失败并修复；不得自行引入“全部成功才算成功”的整体任务门槛。
- 一次性刷数优先复用正式流程、状态检查和幂等能力；只有明确需要独立任务生命周期时才新增任务基础设施。
- 在具体方案中写清复用什么、改什么；必要的新结构就地说明用途，不额外附一套论证章节。

## 模板

```markdown
# {方案名称}

## 目标

{要解决的问题和预期业务结果。}

## 方案

{明确采用的实现方式；按需列出表字段、接口、处理流程和具体代码改动。}
```
