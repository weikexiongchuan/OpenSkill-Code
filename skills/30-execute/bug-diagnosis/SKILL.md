# Bug Diagnosis

## Persona

**侦探型诊断师** -- 执行期间必须：
- 先复现，后推断，不凭猜测
- 每个假设必须有验证手段
- 缩小范围用二分法，不广撒网
- 区分根因和表象，修根因不修表象

## Flow

### Phase 1: 收集症状

向用户确认：
- 什么行为错了（实际 vs 预期）
- 何时开始（最近改动？一直存在？）
- 复现条件（必现/偶现/特定输入）
- 错误日志/截图/堆栈

记录到 `workspace/{project}/notes/bug-{id}.md`

### Phase 2: 复现

1. 根据症状构建最小复现路径
2. 能复现 → 继续 Phase 3
3. 不能复现 → 追问更多上下文（环境/数据/时序差异）

### Phase 3: 缩小范围

二分法缩小：

| 维度 | 方法 |
|------|------|
| 代码 | git bisect / 逐模块排除 |
| 数据 | 简化输入到最小复现集 |
| 时间 | 查 git log 定位引入时间 |
| 配置 | 逐项恢复默认值 |

### Phase 4: 定位根因

1. 读嫌疑代码（必须读，不猜）
2. 构建假设："因为 X，所以 Y 异常"
3. 验证假设：加日志/断点/单元测试/改一行看效果
4. 不成立 → 排除，构建新假设
5. 成立 → 确认根因

涉及异步任务、队列、调度、父子任务、重试、租约、多阶段流程或跨服务状态同步时，必须继续执行 [状态任务生命周期正确性规范](../../../docs/stateful-workflow-correctness.md)：还原完整因果链，穷举同一状态机的全部入口、出口、异常分支和重启入口，不能定位到首个异常后就停止。

### Phase 4.5: 检查同类遗漏

1. 用完整状态与操作矩阵检查父子终态是否闭包
2. 检查永久失败对象是否会阻塞其他对象，队列是否存在饥饿
3. 检查每条重试、等待和租约路径是否有退出条件
4. 检查进程在每个状态写入点和外部调用点退出后的恢复结果
5. 检查事务锁范围、调度线程和部署后的实际工作线程活性
6. 区分已触发的直接根因与尚未触发的同类缺口，分别给出代码证据

### Phase 5: 输出报告

```markdown
# Bug 诊断: {id}
## 症状
（实际 vs 预期）
## 复现路径
（最小步骤）
## 根因
（文件:行号，因果链）
## 影响范围
（哪些功能受影响）
## 同类遗漏
（同一生命周期内已确认的其他缺口及证据）
## 修复建议
（代码根因、异常数据处理、重启恢复、部署后工作线程验证）
```

保存到 `workspace/{project}/notes/bug-{id}.md`

## Rules

| 规则 | 说明 |
|------|------|
| 先复现后定位 | 没复现就没诊断 |
| 读代码不猜代码 | 定位前必须读嫌疑文件 |
| 假设必须可验证 | 每假设配验证手段 |
| 区分根因和表象 | 修复建议指向根因 |
| 生命周期必须穷举 | 状态任务必须检查完整状态机和同类遗漏，不能停在首个异常点 |
| 不擅自修复 | 诊断完输出报告，修复由 bug-fix-workflow 接管 |

## Route

- 上游：用户报告 bug 或异常
- 下游：诊断完成 → `bug-fix-workflow` 接管修复
- 需理解代码 → 读 `10-understand/` 或项目文档

## Self-check

1. 成功复现 bug
2. 根因定位到具体文件和行号
3. 因果链清晰（X 导致 Y 导致 Z）
4. 影响范围已评估
5. 状态任务已完成生命周期和同类遗漏检查
6. 诊断报告已保存
