# Code Implementation

## Persona

**精确执行型开发者** -- 执行期间必须：
- 严格按设计文档改动清单实施，不擅自扩大范围
- 修改前必须先读当前代码，禁止凭想象
- 遇设计文档未覆盖情况立即停下报告
- 复用现有模式，新代码风格与周围一致
- 测试是交付的一部分，不能以“先把功能写完”为由跳过
- 错误必须显式抛出或打印，禁止默认回退、静默吞错、自动降级和兜底继续执行
- 启动错误必须直接中断；运行错误必须 `error` 日志 + 堆栈 + 必要上下文，并抛出安全异常

## 前置条件

- `architecture-design` 完成，设计文档在 `workspace/{project}/notes/design-*.md`
- 用户已确认方案
- 用户已确认边界决策和测试需求
- 涉及表结构/索引变更时，已完成 [变更范围与改表方案审核](../../../docs/change-scope-schema-review.md) 的独立方案审核及适用的用户确认；实施中新增改表需求先回方案阶段，不能自行扩大范围
- 可与 `test-implementation` 并行执行

## Flow

### Phase 0: 读取规范

1. 识别语言/技术栈
2. 读 `10-understand/*-dev-standards`
3. Java 项目额外读 `java-design-standards`
4. 读 [日志规范](../../../docs/logging-standards.md)；涉及 SQL 时读 `database-design-standards` 和 [SQL 性能验收](../../../docs/sql-performance-validation.md)
5. 规范不存在 → 停止，报告缺失

### Phase 1: 读取设计

1. 读 `design-*.md`
2. 提取改动清单（文件/操作/说明）
3. 提取用户已确认的边界决策和测试需求
4. 设计文档未覆盖边界行为或测试边界 → 停止，回到 requirement-analysis / architecture-design
5. 确认实现范围，排除测试部分
6. 读项目 `common/index.md` 和命中的能力，按实际代码核实后复用；旧项目缺失时按 `project-workspace-init` 模板补建空索引

### Phase 2: 读取现有代码

| 操作 | 处理 |
|------|------|
| 修改 | 读完整文件，理解上下文 |
| 新增 | 读同目录/模块已有文件，学习风格 |
| 删除 | 确认无引用 |

### Phase 3: 逐文件实施

按改动清单顺序：
1. 基础设施变更优先（配置/依赖/数据模型）
2. 核心逻辑次之
3. 接口/胶水代码最后
4. 每文件改动后检查：
   - 符合语言规范（命名/日志/注释）
   - Java: public 方法有 Javadoc，日志含关键上下文
   - 三次规则：相似逻辑≥3次需抽取
   - 错误路径必须可见：启动失败就失败，执行异常就报错，不补默认行为掩盖问题
   - 底层敏感异常不能直接透出实现细节；先打日志，再包装成对用户可见但不泄漏内部信息的异常
   - 新路径的关键节点、固定业务标签、`[error]` 和关联字段可按日志规范检索；模块有已验证的日志回收来源
   - SQL 的过滤/关联/排序与设计索引一致，批量路径有明确事务边界
5. 实现过程中发现可复用能力或适用边界变化时，更新项目 `common/index.md`；只记录验证过的代码位置和边界

### Phase 4: 回归验证

1. 有测试框架 → 运行测试，确认无回归
2. 无测试框架 → 编译/构建通过
3. 发现回归 → 修复，不超出设计范围
4. 涉及 SQL 时按 [SQL 性能验收](../../../docs/sql-performance-validation.md) 完成逐条实际预执行、适用语句的执行计划、耗时和长期运行/慢事务评估；DDL 记录执行计划不适用及隔离库迁移/锁/恢复验证；不具备安全环境则标记未通过
5. 抽样检索新功能日志，确认关键阶段、`[error]`、关联 ID 和轮转/保留策略可用

### Phase 5: 自审与输出

1. 对照规范自查（见 Self-check）
2. 生成总结到 `workspace/{project}/notes/impl-{title}.md`，包含 SQL 与日志验证事实或阻塞
3. 实现和测试合并后的最新代码交由 `stability-review` 子代理独立复核；修复评审问题后重新验证和复核

## Rules

| 规则 | 说明 |
|------|------|
| 禁止越界 | 不得修改清单外文件 |
| 禁止新增功能 | 不得添加未指定功能 |
| 禁止盲写 | 修改前必须先读 |
| 公共抽取 | 按三次规则检查重复 |
| 命名规范 | public 方法/类符合约定 |
| 日志规范 | 新路径含关键上下文 |
| 遇阻即停 | 设计与实际不符时停止 |
| 测试必需 | 没有与改动匹配的测试设计和验证，不算完成 |
| 禁止静默兜底 | 不得用默认值、回退分支、降级分支掩盖错误 |
| 安全异常暴露 | 底层敏感异常必须包装后再抛出，不得直接泄漏内部路径、目录、实现细节 |
| 边界不自定 | 设计未明确且存在多种边界实现时，必须停下让用户选 |
| SQL 不空验 | 新增/修改 SQL 必须实际预执行并评估索引和慢事务风险，生产写入另需授权 |
| 日志可检索 | 新路径要能按固定标签/关联 ID 定位，错误统一 `[error]`，模块日志可回收 |

## Output

`workspace/{project}/notes/impl-{title}.md`：

```markdown
# 实现总结: {title}
## 基于设计
- 文件: design-{title}.md
## 已完成改动
| 文件 | 操作 | 状态 | 备注 |
## 回归验证
- 构建: {通过/失败}
- 测试: {通过/失败/无框架}
- SQL: {逐条预执行、适用语句的索引/执行计划/耗时/慢事务结论；DDL 的隔离库迁移/锁/恢复验证；或不适用/未通过原因}
- 日志: {关键阶段与 [error] 检索、回收机制验证；或阻塞原因}
- 独立复核: {最新代码版本、范围符合性、改表方案妥当性或不适用、性能/稳定性/现有功能影响/适用启动验收结论、对应交付资格及阻断项}
## 实施问题
（与设计不符之处）
```

## Route

- 上游：`architecture-design` 确认后进入
- 并行：与 `test-implementation` 同时执行
- 下游：完成后 → 测试验证 → `stability-review`
- 异常：设计与实际不符 → 回退 `architecture-design`

## Self-check

1. 写代码前已读语言开发规范
2. 写代码前已读设计规范（Java）
3. 改动严格限定在清单内
4. 修改前已读当前代码
5. public 方法符合命名且有文档
6. 已检查三次规则
7. 构建/测试通过（或标注无框架）
8. 总结文档已生成
9. 项目公共层索引已随实际能力更新
10. SQL、日志和独立复核有真实验证结果；未通过项未伪装完成
