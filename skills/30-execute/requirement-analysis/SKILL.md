# Requirement Analysis

## Persona

**反驳型分析师** -- 在本 skill 执行期间，AI 必须在每一步自问：

1. 用户的需求到底是什么？
2. 我是否已经 100% 理解全部需求，没有任何偏差？
3. 我下一步该做什么？
4. 我该怎么做？
5. 有没有信息是我还不知道的？

不要假设，不要脑补，不要跳过模糊地带。遇到不确定的点，必须追问用户。

## Flow

### Phase 1: 收集与追问

1. 接收用户需求描述。
2. **读取项目 workspace**：先读 `workspace/{project}/overview.md` 了解现有架构和模块，读 `progress.md` 了解当前状态；再读 `common/index.md` 与命中的可复用条目，缺失则标记待补建。
3. **读取项目代码**：根据需求涉及的模块，读取对应的 CLAUDE.md 和关键代码，理解现有流程；用代码核实公共层条目仍有效。
4. **逐条拆解**：把用户描述拆成独立的需求点，标记每个点的确定性（明确 / 模糊 / 未提及）。
5. **边界清单先行**：必须显式列出正常、异常、空值、重复、并发、时序、窗口清理、错误暴露、协议兼容等边界。
6. **反驳式追问**：对每个模糊、未提及或存在多种实现方式的边界，向用户提出具体问题并让用户选择。不要一次问太多，每轮最多 3 个问题。
7. **验证范围**：记录用户明确的特殊验收要求；业务语义明确时按 [最小验证原则](../../../docs/testing-scope.md) 选择测试，不要求用户逐层确认测试策略。
8. 将用户回答的关键信息写入 `workspace/{project}/notes/` 留存。

### Phase 2: 生成需求文档

当所有需求点都标记为"明确"后，生成需求文档，结构如下：

```markdown
# 需求分析: {需求标题}

## 背景
（为什么要做这个需求，解决什么问题）

## 用户旅程
### 旅程 1: {角色} - {场景}
1. 用户做了什么
2. 系统响应了什么
3. 用户看到了什么
...

### 旅程 2: ...
（按需多条旅程）

## 现有流程分析
（当前系统是怎么处理的，哪里需要改动）

## 最优实现路径
（改动范围最小、风险最低、效果最好的方案方向）

## 影响范围
- 涉及模块:
- 涉及接口:
- 涉及数据:

## 待确认项
（如果还有）

## 边界决策
| 边界点 | 可选实现 | 用户选择 |
|-------|---------|---------|

## 测试需求确认
| 测试层 | 必测边界 | 用户确认 |
|-------|---------|---------|

## 决策记录
| 问题 | 用户决策 | 日期 |
|------|---------|------|
```

### Phase 3: 用户确认

- 将需求文档呈现给用户。
- 用户确认用户旅程无误后，本 skill 结束，进入方案设计阶段。
- 用户有修改意见时，回到 Phase 1 继续追问和修正。

## Output

- 需求文档保存到 `workspace/{project}/notes/req-{kebab-case-title}.md`
- 关键决策同步追加到 `workspace/{project}/progress.md`

## Route

- 用户旅程确认后 → 进入方案设计（`20-plan/` 中的方案设计 skill 或直接 plan mode）
- 分析过程中发现对现有代码不了解 → 读取 `10-understand/` 或项目文档
- 需要更新服务器或项目状态 → 切到 `30-execute/project-state-record-update`

## Self-check

1. 是否读取了现有项目架构再分析，而不是凭空设计
2. 是否每个模糊点都追问了用户，而不是自己假设
3. 用户旅程是否从用户视角描述，而不是从技术实现视角
4. 最优路径是否核对了项目公共层、改动范围和风险
5. 关键信息是否已写入 workspace 留存
