# Stability Review

## 前提与分工

- 主代理先完成实现、测试和适用的 SQL/日志验收，再用可用的**子代理工具**派发独立只读评审；自我复查不能替代子代理。若环境没有子代理工具，明确报告该项未完成，不得写成通过。
- 派发时提供当前提交、工作区最新 diff、设计/需求、测试结果、SQL 执行计划与实测、日志验证结果；评审者自行读取最新文件，不依赖主代理结论。用户已有未提交改动应明确区分归属。
- 必须先读 [变更范围与改表方案审核](../../../docs/change-scope-schema-review.md)，按其派发要求提供用户原话、已确认方案、后续限制及授权边界；范围扩大和改表妥当性不能仅附在代码性能结论中。
- 必须将该文档“业务必要性前置”约束加入派发提示词；评审者先挑战需求到机制的推导，再审核内部正确性，不能把主代理设计当用户要求。优先核对既有状态、存储与统一调用模块是否已经够用。
- 若实现或测试继续改动，旧评审结论失效；针对最新代码重新评审。

## 必查维度

先分别给出**范围符合性**和**改表方案妥当性**结论，再检查以下四项。涉及表结构/索引时核实方案阶段的独立审核及确认依据；没有相关变更写“不适用”。

1. **性能**：SQL 索引与实际执行计划、长期运行/慢事务、批量与并发、热点路径复杂度、资源占用；有 SQL 时按 [SQL 性能验收](../../../docs/sql-performance-validation.md) 核实真实预执行证据。
2. **稳定性**：错误传播、超时/重试/幂等、并发与状态收敛、资源释放；按 [日志规范](../../../docs/logging-standards.md) 核查关键节点、统一 `[error]` 标签、关联链路与日志回收。
3. **现有功能影响**：接口/事件/数据兼容性、未改动路径的回归、配置和部署行为、测试覆盖；检查用户要求外的功能或行为变化。
4. **启动与装配**：按 [发布包启动验收](../../../docs/release-startup-validation.md) 查完整应用中新增注入类型的全部候选与条件配置，核对真实容器测试是否覆盖目标启用组合；发包/部署时核验最终制品启动、就绪、健康及哈希证据。手工创建配置类、关闭业务域的启动测试和包结构检查均不能替代此项；缺少证据明确报告发布验收未完成。

## 输出与闭环

- 按严重度列出可复现的问题，注明文件/位置、触发条件、证据和影响；没有发现也要分别给范围、改表及四个技术维度的结论和检查范围，不把“未检查”说成“无问题”，不把源码审核通过写成最终发布包启动通过。
- 未获确认的范围扩大、改表方案不妥当或关键评估未完成均阻断对应变更交付；不能以无P0/P1、测试全通过或小型隔离库改表成功判定整体通过。用户新增限制后重新审核当前实现。
- 主代理修复确认的问题后重跑相关测试与 SQL/日志验收，再让子代理复核**最新** diff；存在高风险未解决项时不得声称稳定性通过。
- 在实现记录中留下评审代码版本、发现、修复和残余风险。子代理只评审，不擅自改代码或生产数据。
