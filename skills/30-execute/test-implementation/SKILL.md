# Test Implementation

## Hard Requirement

- 先按 [最小验证原则](../../../docs/testing-scope.md) 选择范围；先判断是否需要测试；小需求、小调整或小修复可仅做差异自查，不进入后续测试流程。需要测试时只选相关用例或复现路径。
- 业务语义已明确时不重复确认测试策略；只有未确认的业务选择才询问。
- 已通过且相关文件/依赖未变的结果可复用，相关失败才阻断对应路径。

## Persona

**严谨型测试工程师** -- 执行期间必须：
- 破坏性思维寻找边界和异常，不信任输入
- 每个测试有明确失败场景预期
- 测试代码与业务代码同等质量
- 独立于 `code-implementation`，可并行执行

## 前置条件

- 需求及受影响行为明确；小修复无需独立设计文档或测试方案。

## Flow

### Phase 0: 读取规范

1. 识别语言，读 `10-understand/{lang}-test-standards` 和 `{lang}-dev-standards`
2. 缺少专项规范时沿用现有项目惯例，不为小修复新建测试规范或框架

### Phase 1: 读取测试方案

从已有方案或明确需求提取改动范围、业务边界及用户指定的验收要求；小任务不补建方案文档。

### Phase 1.5: 边界与测试需求确认

1. 用 challenger 视角复核测试边界：正常、异常、空值、重复、并发、时序、窗口清理、错误暴露、协议行为
2. 只询问会改变业务结果的未明确边界
3. 测试层级、数量和范围由代理按风险选择，不逐项让用户决策

### Phase 2: 基线验证

1. 需要对照时只运行相关测试；可复用已有有效基线，不默认全量
2. 失败先判断关联性；相关问题定位修复，无关失败记录
3. 足以验证修复后继续交付，不追加机械复测

### Phase 3: 测试用例设计

| 类型 | 覆盖 | 最低要求 |
|------|------|---------|
| 单元 | 实际变化的业务规则 | 选择能暴露回归的代表场景 |
| 集成 | 模块交互确有变化 | 仅关键受影响路径 |
| 边界 | 本次改变的边界或并发 | 按实际风险选择 |
| 错误 | 本次改变的失败处理 | 覆盖关键结果，不机械遍历catch |

### Phase 4: 实现测试

1. 按规范编写（AAA模式/命名/隔离）
2. Mock策略：只mock外部依赖（DB/HTTP/MQ），不mock被测类
3. 有多个有意义输入时用参数化测试，不设固定case数量
4. 复杂对象用Test Data Builder，setup不超过10行

### Phase 5: 相关验证

| 检查项 | 预期 | 失败处理 |
|--------|------|---------|
| 受影响的既有测试 | 与基线一致 | 排查是否破坏功能 |
| 新增测试 | 100%通过 | 修复或标记设计问题 |
| 变更测试 | 变更后通过 | 确认可追溯需求 |
| 关键风险覆盖 | 足以判断本次变化 | 只补缺失的关键证据，不设统一覆盖率 |

既有测试变更 → 理由追溯需求文档具体条目

### Phase 6: 生成报告

小修复在回复或既有记录中简述结果；复杂变更需要独立报告时保存到 `workspace/{project}/notes/test-{title}.md`：

```markdown
# 测试报告: {title}
## 基线结果
## 新增测试
| 类 | 方法 | 覆盖点 | 状态 |
## 变更测试
| 类 | 变更 | 关联需求 | 状态 |
## 本次验证结果
（通过/失败/跳过/覆盖率）
## 风险项
（未覆盖边界/已知局限）
```

## Rules

| # | 规则 | 违反后果 |
|---|------|---------|
| 1 | 区分相关与无关失败 | 相关失败才阻断对应路径 |
| 2 | 测试间无共享可变状态 | `@BeforeEach` setup |
| 3 | 一测试一逻辑断言 | 禁止多断言掩盖失败 |
| 4 | 只mock外部依赖 | 禁止mock被测类 |
| 5 | 既有测试变更须追溯 | 禁止无理由修改 |
| 6 | 按风险选用例 | 不为覆盖率数字增加测试 |
| 7 | 复用既有测试惯例 | 不为小修复新增框架/规范 |
| 8 | 业务歧义才确认 | 常规测试策略由代理选择 |

## Output

- 测试代码（按项目test source root放置）
- 按任务规模简述结果或写既有记录；独立报告按需

## Route

- 上游：`architecture-design` 确认后进入
- 并行：与 `code-implementation` 由sub-agent并行，共享设计文档
- 下游：相关验证通过 → 合并主流程
- 异常：相关验证失败 → 定位处理；不因无专项规范停止

## Self-check

1. 已读 test-standards 和 dev-standards
2. 已有基线可复用时不重跑
3. 本次关键变化有适当验证
4. 测试遵循AAA且独立
5. 变更测试有需求追溯
6. 未机械扩大测试范围或追逐覆盖率
7. 验证结果已简述，不强制另建报告
